8. Why StandardScaler?

Your seven features are on very different scales.

For example:

rating_entropy        → small numerical range
reviews_per_day       → potentially much larger
review_burst_7d       → integer counts
burst_ratio_7d        → 0–1

If these are directly fed into a model, the scales aren't comparable.

So you use:

StandardScaler()

which essentially standardizes each feature relative to the training population.

The important interview phrase is:

And your inference function correctly uses:

44. Your 2–3 minute mentor/interview explanation

Here is the version I'd recommend memorizing:

Our project is a Hybrid Review Authenticity Detection System. The main idea is that detecting suspicious reviews should not depend only on the review text. A reviewer can also exhibit unusual behavioral patterns, so we analyze both reviewer behavior and review text as two independent signals.

For the behavioral component, we use an Amazon review dataset that does not contain fake or genuine labels. Therefore, instead of using supervised classification, we formulate behavioral analysis as an unsupervised anomaly-detection problem.

First, we convert the review-level data into a reviewer-level dataset by grouping reviews according to reviewer ID. From the review history, we engineer behavioral features such as rating variance, rating entropy, reviews per day, seven-day review bursts, burst ratio, average days between reviews, and burst intensity. Burst intensity is calculated from the seven-day review burst and its ratio to the reviewer's total reviews.

Our EDA showed that most reviewers have relatively low review activity, while some reviewers exhibit unusually high review frequencies or concentrated bursts of reviews. Because bursty reviewing behavior appeared to be an important suspicious signal, the final model includes several burst-related features.

We experimented with Isolation Forest and also compared it with Local Outlier Factor and One-Class SVM. We additionally tested contamination values from 0.01 to 0.04. After manually inspecting borderline reviewers, we retained Isolation Forest with 200 trees, contamination of 0.02, and random state 42.

The final pipeline first applies log1p to average days between reviews and then uses a fitted StandardScaler. The scaled seven features are passed to the trained Isolation Forest. Instead of relying only on its binary anomaly prediction, we use its continuous decision function and convert that value to a 0–100 Behavior Score using a fitted MinMaxScaler. A high Behavior Score means the reviewer's behavior looks more normal, while a low score indicates more anomalous behavior. Importantly, this is not a probability that the reviewer is fake.

The trained behavioral pipeline is saved using three files: scaler.pkl contains the fitted StandardScaler, isolation_forest.pkl contains the trained Isolation Forest, and score_scaler.pkl converts the raw decision score into the 0–100 Behavior Score. We also validated the inference function by reloading these artifacts and reproducing the stored score for an existing reviewer.

The second component is the NLP module, which is being developed separately. Its planned workflow is to preprocess a labeled review dataset, convert text into TF-IDF features, evaluate models such as Logistic Regression, Linear SVM and Naive Bayes, and select the best-performing model based on metrics such as precision, recall and F1-score. It will ultimately provide a Text Authenticity Score from 0 to 100.

The next stage is integration. The Streamlit application will accept the current review text and reviewer information or reviewer history. Historical reviews will be used to calculate the behavioral features, while the current review text will be passed to the NLP model. The two resulting scores will then go into an explainable Decision Engine, which will produce a Final Authenticity Score and an explanation.

For example, if both behavioral and text scores are high, the review would be considered likely authentic. If both are low, it would be highly suspicious. If they disagree, the system should report the conflicting evidence rather than automatically calling the review fake.

For reviewers with insufficient history, the behavioral score should be marked unavailable rather than being fabricated, and the system can rely on the available NLP signal. This gives the final system a modular architecture where behavioral analysis, NLP analysis, decision logic and the Streamlit interface can be developed and tested independently.

Bottom line

Your behavioral work is genuinely at the integration-ready stage. You have the feature engineering, EDA, model experimentation, final Isolation Forest, three saved artifacts, reusable inference function, and validation of the saved pipeline.

What you do not have yet in this ZIP is the completed NLP implementation, Decision Engine, or Streamlit integration. So your immediate job is not to retrain the behavioral model. It's to package that finalized pipeline cleanly, get the NLP member's model exposed through a simple inference interface, define the score-combination/missing-history logic, and then build Streamlit around those modules.
